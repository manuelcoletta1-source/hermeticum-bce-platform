Privacy Policy

HBCE Platform is designed around data minimization, local-first evidence handling, hash-only public verification, and fail-closed registry semantics.

The public layer is a documentation and verification gateway. It must not become a public custody layer for identity documents, private evidence, credentials, secrets, raw personal identifiers, or sensitive operational payloads.

Policy: GDPR-min · hash-only · fail-closed · append-only · no public data custody · EU-first

1. Privacy posture

The privacy model of the public HBCE Platform is based on minimizing what is published, separating public proof from private evidence, and using hash commitments instead of raw sensitive payloads wherever possible.

  • GDPR data minimization — only the minimum public proof material should be exposed.
  • No public identity custody — the public layer should not store full identity records or identity documents.
  • Hash-only public verification — public verification should rely on minimized hash commitments.
  • Local-first evidence handling — complete evidence files remain under the control of the holder or authorized private process.
  • Append-only registry discipline — public proof records should be extended, not silently rewritten.
  • Fail-closed validation — missing, invalid, malformed, or ambiguous records must not produce validity.

2. Public registry data

The public registry should contain only minimized public proof records. Under the current registry v3 model, public entries should use fields such as:

  • entity_type
  • subject_label
  • record_scope, when needed
  • payload_sha256
  • timestamp
  • status
  • short non-sensitive public notes, when needed

Public labels are not intended to replace private identity verification. A public proof record only means that a minimized public commitment is present in the public registry.

3. Data not allowed in the public layer

The public repository and public registry must not contain:

  • API keys;
  • private keys;
  • passwords;
  • authentication tokens;
  • credentials;
  • raw personal identifiers;
  • tax codes or fiscal codes;
  • identity documents;
  • private identity evidence;
  • private communications;
  • confidential customer data;
  • production logs containing personal data;
  • sensitive operational payloads;
  • private endpoints, private infrastructure details, or internal credentials.

4. Local-first evidence handling

Full evidence files, identity materials, receipt preimages, private proofs, and sensitive operational records should remain outside the public repository and outside the public registry.

The public layer may publish a hash commitment or minimized proof reference, but the complete evidence should remain under the control of the holder, maintainer, authorized organization, or lawful private review process.

5. Verification

Verification is performed through deterministic comparison against public proof commitments, primarily using payload_sha256 and registry v3 semantics.

  • valid match → PUBLIC_RECORD_PRESENT;
  • missing match → NO_PUBLIC_RECORD;
  • invalid input → INVALID;
  • unreachable or malformed registry → NON_OPERATIONAL.

A public match does not replace private evidence review, identity verification, contractual qualification, legal authorization, or institutional validation.

6. Cookies, analytics, and tracking

The public HBCE Platform should avoid unnecessary tracking and unnecessary analytics. If analytics or third-party services are introduced in the future, they should be documented clearly and configured consistently with data minimization principles.

Public GitHub Pages hosting may generate standard technical logs under the hosting provider’s own policies. This repository does not use those logs as an identity-custody system.

7. Security reports and exposed data

If secrets, credentials, personal data, identity documents, private evidence, or sensitive operational payloads are discovered in the public repository or public registry, they should be reported according to SECURITY.md.

Do not copy, redistribute, exploit, or amplify exposed sensitive material.
