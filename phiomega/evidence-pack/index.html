What is an Evidence Pack?

An Evidence Pack is a portable, tamper-evident archive for a real machine (robot/PLC/cell). It contains identity, events, propositions, and chained evidence records. The pack can be verified deterministically.

  • Hash-only: evidence is represented as hashes (no public data custody).
  • Append-only: records are hash-chained (edits become detectable).
  • Fail-closed: if integrity is broken → verification fails (NO MATCH).

Deliverables (D1/D2/D3)

D1 — Machine Identity Pack (MIP)

Identity envelope: machine_id, layered fingerprints, policies, chain genesis hash. Delivered as JSON (public/minimal and optional private version).

D2 — Evidence Log (append-only)

A chain of events and evidence records. Each record contains a prev_hash, forming an immutable-like sequence within the pack.

D3 — Deterministic Verify

A verification procedure (or tool) to check a record/hash and confirm: MATCH (integrity intact) or NO MATCH (tampered / broken chain).

  manifest.json
  identity/
    mip.public.json

    ...
  propositions/

    ...
  verify/
    verify.md
    (optional) verify.html / verify-cli
  report/
    pilot-report.pdf (or .html)

Packs can be zipped and stored internally. No external services are required to validate internal chaining.

Record chaining (append-only)

Every event carries a prev_hash field, and every evidence record references the hash of the previous record. This creates a chain where tampering breaks verification deterministically.

Event (Λ) example

{
  "proto": "PHIOMEGA-EVENT-v0.1",
  "isoTime": "2026-02-20T16:30:00+01:00",
  "machine": { "machine_id": "CN-PILOT-001", "source": "PLC" },
  "event": { "type": "JOB_START", "severity": "INFO", "job_id": "JOB-000042" },
  "security": {
    "nonce": "b64:4yQm...==",
    "prev_hash": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}

Evidence record example

{
  "proto": "PHIOMEGA-RECORD-v0.1",
  "record_id": "REC-20260220-000001",
  "ref_event_hash": "sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "prev_record_hash": "sha256:cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "hash": "sha256:dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd",
  "status": "OPPONIBLE_READY",
  "note": "Pilot mode: technical integrity + deterministic verification"
}

Deterministic verification (MATCH / NO MATCH)

Verification is deterministic and offline-capable. The verifier recalculates hashes and checks chain continuity.

Verification steps

  1. Pick a target record (by record_id or hash).
  2. Recompute the record hash from canonical JSON fields.
  3. Check that prev_record_hash matches the previous record hash.
  4. Walk backward (or forward) to the genesis hash from MIP.
  5. If any mismatch occurs → NO MATCH. If all checks pass → MATCH.

This is the core advantage: no “trust me”. Either it matches, or it doesn’t.
