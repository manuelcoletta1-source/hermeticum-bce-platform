2. Why the active form is removed

Earlier versions of the operator-license concept could be read as active onboarding or licensing. That creates overclaim risk because the platform is currently an R&D/MVP environment, not a regulated operator authority.

Any previous form that collected real name, email, IPR reference, location or application fields must be treated cautiously. Even if local-first, such a form could be misread as a legal operator-license workflow, professional qualification process, KYC process or active operator network onboarding.

Future operator qualification workflows, if developed, require separate legal, privacy, cybersecurity, contractual, institutional and operational review before any real use.

3. Correct operator interpretation

In the current R&D/MVP boundary, an operator should be understood only as an operational role reference inside an IPR-linked governance workflow. The useful technical purpose is to connect action, validation, responsibility, event continuity and proof material.

Public proof presence does not equal operator authorization. A public record only indicates that a minimized proof reference exists.

4. Current public proof model

Any future operator proof should follow the current HBCE public proof model: 

Private or controlled evidence
→ canonical hash commitment
→ payload_sha256
→ registry v3 public record
→ deterministic verify
→ PUBLIC_REFERENCE_PRESENT / NO_PUBLIC_RECORD / INVALID / NON_OPERATIONAL

The public registry is a minimized R&D proof-reference surface. It is not a public authority registry, not a civil identity registry, not a professional register and not a legal certification register.
