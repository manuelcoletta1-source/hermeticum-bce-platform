Non-negotiable design principle

This layer does not control motors, servo loops, or safety hardware. It controls authorization and accountability for actions before execution.

  • Robot stack owns: safety PLC, E-Stop, motion control, stability.
  • HBCE layer owns: identity gate, policy gate, audit proof, execution token.

Edge-first components

A · Binding Gateway (EDGE)
  • Single entry point for sensitive actions.
  • Interfaces: REST/gRPC, ROS2 services/actions, MQTT, OPC-UA bridge.
  • Output: ALLOW/DENY + reason code, execution token (short TTL).
B · Identity Resolver (EDGE)
  • Resolves and verifies operator IPR, machine IPR, context IPR.
  • VALID must be deterministic (registry presence + hash match).
  • Short TTL cache allowed (performance), always invalidable.
C · Policy Engine (EDGE)
  • Deterministic rule execution. Versioned and hash-bound.
  • Examples: roles, time window, thresholds, geofencing, two-man rule, escalation.
  • Format: HBCE-POLICY-INDUSTRIAL-v1 (JSON, immutable by hash).
D · Ethical Governor (EDGE)
  • Does not run motion control.
  • Reads robot state/telemetry and blocks/conditions high-risk actions.
  • Examples: torque/speed thresholds, human proximity, restricted zones, unsafe state machine.
E · Evidence Builder (EDGE)
  • Builds: DecisionRecord, BindingEvent, Receipt, PackManifest.
  • Private custody: evidence pack (customer).
  • Public custody: hash-only proof (registry).
F · Proof Emitter (EDGE → Registry)
  • Emits hash-only append-only entries.
  • Default posture: strict fail-closed (proof not emitted → block).
  • Degraded mode exists only if explicitly defined and auditable.
G · Local Ledger (EDGE)

Append-only local ledger for resilience and forensics. Required for real factories where connectivity can fail. Local ledger events are chained by hash and sealed periodically.

Operational flow

  1. Request — A sensitive action is requested (START_CYCLE, MOVE_HOME, CHANGE_PARAM, DEPLOY, etc.).
  2. Identity Gate — operator IPR VALID? machine IPR VALID? context IPR VALID?
  3. Policy Gate — deterministic policy evaluation (roles, thresholds, approvals, time window).
  4. Decision — ALLOW / DENY / REQUIRE_DUAL_APPROVAL with reason code.
  5. Binding — bind decision to identity + policy hash + software fingerprint.
  6. Execution Token — short TTL token (30–120s) accepted by controller / gateway.
  7. Evidence — build private pack + emit public hash-only proof (append-only).

Industrial claim: show who authorized a machine action, with which identity, and prove it months later.

Fail-closed decision matrix

Condition Result Reason-code example
Operator IPR missing / non-VALID BLOCK IDENTITY_INVALID
Machine IPR missing / non-VALID BLOCK MACHINE_ID_INVALID
Policy mismatch / non-deterministic verification BLOCK POLICY_FAIL
High-risk action without required approvals BLOCK RISK_HIGH
Evidence pack not generated BLOCK EVIDENCE_FAIL
Proof emission fails (strict mode) BLOCK PROOF_EMIT_FAIL
Execution token expired BLOCK TOKEN_EXPIRED

Degraded mode is optional and must be explicit, auditable, and time-bounded. Default posture is strict fail-closed.

Integration profiles

P1

API Gate

Robot/fleet accepts commands via API. Place gateway in front of it. Best for drones, fleets, software-controlled robots.

P2

ROS2 Gate

Gateway as ROS2 node. Authorizes action requests, issues tokens, publishes allowed commands. Best for research humanoids and advanced robotics.

P3

Industrial Bridge

MES/SCADA/OPC-UA → gateway → controller. Best for industrial automation and production lines.

Security minimum (practical)

  • Replay protection: nonce + TTL.
  • Role gating: least privilege.
  • Log tamper resistance: hash chain + periodic sealing.
  • Bypass resistance: network segmentation + allowlists.
  • Key hygiene: rotation + secure storage (where available).

MVP deliverables (90-day build target)

  • Binding Gateway (P1) + Policy Engine v1.
  • Identity Resolver with deterministic VALID checks.
  • Evidence Builder: pack + manifest + receipts.
  • Proof Emitter: hash-only append-only public entries.
  • Demo scenarios: allow/deny, two-man rule, threshold deny, reproducible verify.
