2. Current public proof model

The previous playbook language referred to legacy registry entries using fields such as nickname. The current public proof model uses registry v3 and payload_sha256. 

Private or controlled evidence
→ canonical hash commitment
→ payload_sha256
→ registry v3 public record
→ deterministic verify
→ PUBLIC_RECORD_PRESENT / NO_PUBLIC_RECORD / INVALID / NON_OPERATIONAL

Public proof presence does not equal operator authorization. It only indicates that a minimized public proof commitment exists.

3. R&D training notes

If future operator workflow training is developed, it should be rebuilt around:

  • registry v3;
  • payload_sha256 as the central public proof field;
  • minimized public labels;
  • no-public-data-custody rules;
  • separation between public proof and private evidence;
  • human validation and responsibility ownership;
  • clear non-claims around legal, institutional and regulated status;
  • defensive and authorized use only.

4. Deprecated operational language

The previous version described a direct E2E operator process. That language has been removed because it could be interpreted as an active license, certification, or onboarding procedure.

Future operational playbooks must only be published after legal review, security review, privacy review, contractual review and a clear distinction between R&D, pilot, and production phases.
