HBCE Protocol v1

Deterministic operational identity protocol for humans, AI agents and autonomous systems operating on European territory. Public evidence is hash-only. Registry is append-only. Validity is fail-closed.

Canonical gateway Public registry Verify

This document describes protocol semantics and operational truth rules. It is written to be auditable and reproducible.

0. Scope

HBCE defines a minimal operational identity layer for critical environments. It introduces:

  • Identity Primary Record (IPR) as a persistent operational identity root.
  • Hash-only public evidence and deterministic verification.
  • Append-only registry discipline.
  • Fail-closed validity (missing proof ⇒ INVALID).

HBCE is an operational identity and auditability layer. It does not claim to replace eIDAS / EUDI Wallet legal identity schemes.

1. Definitions

TERM
IPR (Identity Primary Record)
Persistent operational identity root. Used to derive operator authority, autonomous unit identities and infrastructure identities.
TERM
Canonical file
A deterministic representation of an identity release used to compute a reproducible SHA-256 digest.
TERM
Public registry entry
Hash-only evidence published append-only. No public custody of personal data. Verification is deterministic.
TERM
Fail-closed validity
Missing or mismatched proof results in INVALID status. No “best effort”. No partial trust.

2. Operational truth (deterministic)

  • VALID = SHA-256(canonical identity file) exists in public registry + integrity checks pass.
  • INVALID = missing match OR mismatch OR integrity failure.
  • Public registry stores hash-only evidence (GDPR-min; no public personal data custody).
  • Registry is append-only. History is never rewritten.

HBCE validity is binary and reproducible. This is required for governance in critical environments.

3. Data custody model

HBCE separates private custody from public verification:

  • Private custody: identity release files remain client-side / operator-side.
  • Public verification: registry contains only hash evidence + timestamps.
  • No public personal data custody: registry never stores identity payloads.

The protocol enforces minimization by construction: public layer never holds identity data.

5. Derivation rules (mandatory)

  • Derived identities must reference a parent identity root.
  • Parent identity must be VALID in the public registry at issuance time.
  • If parent is not VALID ⇒ issuance MUST STOP (fail-closed).
  • Autonomous systems and AI units operate under derived identities.

Derivation is the enforcement mechanism that binds humans, operators and autonomous units into a deterministic identity graph.

6. Implementation constraints

  • GitHub Pages has no server-side writes: registry append is manual by design (auditable).
  • Deterministic hashing requires canonicalization rules (stable ordering, stable encoding).
  • Public verification must be reproducible in independent environments.
