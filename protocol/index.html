HBCE Protocol v1 — Official Specification

Deterministic operational identity infrastructure for humans, AI, autonomous machines and critical systems. Public registry is hash-only and append-only. Verification is fail-closed.

Core Properties

  • Hash-only: public registry exposes cryptographic proofs only (no public custody of personal data).
  • Append-only: history cannot be erased; changes are events.
  • Fail-closed: if verification fails → INVALID.
  • Audit-first: every state transition is reconstructible.
  • Derivation integrity: derived identities require a valid parent.

Record Model

HBCE defines a small set of public record types for the registry. Private payloads are stored off-registry; only payload hashes are published.

IPR Root Record

Root identity for humans, institutions, corporates, AI. This anchors the derivation tree. 

{
  "kind": "IPR_ROOT_RECORD",
  "entity_id": "IPR-ROOT-…",
  "entity_type": "HUMAN_ROOT|INSTITUTION_ROOT|CORPORATE_ROOT|AI_ROOT",
  "payload_sha256": "…",
  "timestamp": "…",
  "status": "VALID|INVALID|REVOKED",
  "issuer": { "sign_alg": "ED25519", "pubkey": "…", "signature": "…" }
}

IPR Derived Record

Derived identity for robots, vehicles, drones, software, infrastructure. Requires parent to be VALID. 

{
  "kind": "IPR_DERIVED_RECORD",
  "entity_id": "IPR-DEV-…",
  "entity_type": "IPR_ROBOT|IPR_VEHICLE|IPR_DRONE|…",
  "parent_entity_id": "IPR-ROOT-…",
  "derivation_type": "DERIVED_FROM_ROOT|…",
  "payload_sha256": "…",
  "timestamp": "…",
  "status": "VALID|INVALID|REVOKED",
  "rules": { "fail_closed": true, "inherit_invalidity": true, "append_only": true },
  "issuer": { "sign_alg": "ED25519", "pubkey": "…", "signature": "…" }
}

IPR Event Record

Append-only event emitted by an operator. Used for firmware updates, critical ops, alerts, decommission, etc. 

{
  "kind": "IPR_EVENT_RECORD",
  "event_id": "EVT-…",
  "entity_id": "IPR-DEV-…",
  "event_type": "FIRMWARE_UPDATE|SECURITY_ALERT|…",
  "event_payload_sha256": "…",
  "timestamp": "…",
  "status": "VALID|INVALID|REVOKED",
  "append_only": true,
  "operator": { "operator_id": "IPR-OP-…", "sign_alg": "ED25519", "pubkey": "…", "signature": "…" }
}

Verification Rules (Fail-Closed)

  • If any required field is missing → INVALID
  • If a hash is malformed (not 64-hex for SHA-256) → INVALID
  • If signature verification fails → INVALID
  • If a derived record has a parent not VALID → INVALID
  • If ledger chain integrity fails (prev pointer mismatch) → INVALID

Reference CLI Flow

The reference toolchain demonstrates deterministic behavior: same input → same canonical JSON → same hash → same verification outcome. 

# 1) Rebuild a self-consistent hash chain
node protocol/hbce-verify.reference.js protocol/hbce-registry-ledger.example.json --rebuild > protocol/hbce-registry-ledger.rebuilt.json

# 2) Generate ED25519 keys
mkdir -p protocol/keys
node protocol/hbce-sign.reference.js --keygen issuer   > protocol/keys/issuer.ed25519.json
node protocol/hbce-sign.reference.js --keygen operator > protocol/keys/operator.ed25519.json

# 3) Sign the ledger with real signatures
node protocol/hbce-sign.reference.js --sign-ledger protocol/hbce-registry-ledger.rebuilt.json protocol/keys/issuer.ed25519.json protocol/keys/operator.ed25519.json > protocol/hbce-registry-ledger.signed.json

# 4) Verify chain + entity
node protocol/hbce-verify.reference.js protocol/hbce-registry-ledger.signed.json --check-chain
node protocol/hbce-verify.reference.js protocol/hbce-registry-ledger.signed.json --verify-entity IPR-DEV-ROBOT-0001
