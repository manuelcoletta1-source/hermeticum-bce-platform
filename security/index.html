SECURITY · IPR ONBOARDING · IPR CARD · JOKER-C2 ACCESS GATE · FAIL-CLOSED

Security starts before JOKER-C2 access.

HBCE Platform treats security as an identity, evidence, access and governance property. The security model begins before runtime access: onboarding, private evidence protection, IPR state control, IPR Card status, public proof minimization and fail-closed access decisions.

The core rule is: no verified operational identity, no governed runtime access. JOKER-C2 must not be treated as a classic AI surface accessed through simple email, password and subscription. It is an AI Operational Runtime whose governed access depends on verified IPR identity, policy, risk and operational authorization.

This page describes a defensive R&D security posture. It is not a formal security certification, SOC report, penetration-test report, third-party audit attestation, regulated KYC / AML assurance, cybersecurity certification or production security warranty.

Security principles

FAIL-CLOSED

No implicit validity

Missing input, malformed hash, invalid registry state, absent public record, inconsistent proof or uncontrolled identity evidence must not produce validity.

PRIVATE VERIFICATION

Evidence stays controlled

Identity evidence, national identifiers, document evidence, selfies, videos and liveness data belong only in a private or controlled verification layer.

PUBLIC PROOF

Hash-oriented exposure

Public verification uses minimized proof references, primarily digest-based commitments such as payload_sha256, rather than exposing private evidence.

APPEND-ONLY

Traceable history

Public history should be extended through new entries, events, commits or findings rather than silently rewritten.

NO PUBLIC CUSTODY

No sensitive public storage

The public layer must not store tax codes, national identifiers, document numbers, identity documents, credentials, secrets, private keys, customer data, production logs or sensitive payloads.

DEFENSIVE SCOPE

Authorized security only

Security work must remain defensive, authorized, non-offensive and limited to repository-owned, explicitly authorized, public or synthetic scenarios.

IPR ACCESS SECURITY

JOKER-C2 access depends on IPR state.

Governed runtime access must be interpreted through explicit IPR state and policy. The runtime must fail closed when identity status is missing, provisional, suspended, revoked, expired or ambiguous.

System security hierarchy

IPR

Operational identity reference

IPR connects an operational identity reference to event context, proof material, responsibility and verification. It is not a legal identity system or public identity-custody database.

IPR CARD

Access-state object

IPR Card represents operational status, verification level, activation EVT, OPC receipt and public proof reference. It is not a state identity document or banking card.

JOKER-C2

Governed runtime demonstrator

JOKER-C2 demonstrates governed AI-assisted workflows. It is not a SOC replacement, incident-response system, command system, autonomous compliance authority or production security platform by itself.

REGISTRY / VERIFY

Public proof and deterministic checks

Registry exposes minimized proof references. Verify checks public proof references. Neither stores private identity material or grants runtime access by itself.

PRIVATE VERIFICATION SECURITY

Identity evidence must never become public repository content.

IPR Verified may require private identity verification. That verification must happen only inside controlled private environments. The public platform must not be used as an identity-document upload surface, tax-code repository, KYC repository or public identity-custody system.

INCIDENT RECONSTRUCTION

Minimum incident reconstruction path

  1. Identify the relevant IPR, IPR Card, public registry entry, EVT reference, OPC proof or audit trace.
  2. Retrieve private evidence only through authorized private channels.
  3. Compute SHA-256 over the controlled artifact.
  4. Compare the result against the public payload_sha256 commitment or expected proof reference.
  5. Review append-only history, audit findings, commits and issue traces.
  6. Fail closed if required evidence is missing, inconsistent or unverifiable.
