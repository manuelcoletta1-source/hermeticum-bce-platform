Security model

HBCE Platform treats security as a governance and verification property: deterministic integrity, minimized public exposure, private verification boundaries, append-only audit traces, defensive use and fail-closed validation.

The current platform is centered on IPR as the operational R&D/MVP product, IPR Verified as the private-verification profile, IPR AI Audit Trail as the first demonstrable use case, HBCE as the operational ecosystem, JOKER-C2 as the runtime demonstrator and MATRIX as the architectural framework.

Policy: defensive security · authorized testing only · private verification · no public tax-code custody · no public identity-document custody · hash-oriented proof · fail-closed

1. Security status

HBCE Platform is an experimental R&D public gateway. Its security model is designed around deterministic verification, private/public evidence separation, minimized public exposure, no public evidence custody and fail-closed behavior.

IPR Verified may require private identity verification based on tax-code and valid identity-document evidence. That verification must happen only inside controlled private environments. The public platform must not be used as an identity-document upload surface, tax-code repository, KYC repository or public identity-custody system.

This page is not a formal security certification, third-party audit attestation, SOC report, penetration-test report, enterprise hardening statement, cybersecurity compliance certification, regulated KYC / AML assurance or production security warranty.

Any production deployment, customer pilot, institutional integration, enterprise use or real identity-verification operation requires separate legal, cybersecurity, privacy, compliance, operational and infrastructure review.

2. Security principles

Fail-closed
Missing input, malformed hash, invalid registry state, absent public record, inconsistent proof or uncontrolled identity evidence must not produce validity.
Private verification boundary
Tax-code and identity-document evidence for IPR Verified belongs only in a private, controlled verification layer. It must not be published to the public repository or public registry.
Hash-oriented public proof
Public verification uses minimized proof references, primarily digest-based commitments such as payload_sha256, instead of exposing private evidence.
Append-only audit
Public history should be extended through new entries, events, commits or findings rather than silently rewritten.
No public data custody
The public layer must not store tax codes, document numbers, identity documents, credentials, secrets, private keys, customer data, production logs or sensitive payloads.
Defensive scope
Security work must remain defensive, authorized, non-offensive and limited to repository-owned, explicitly authorized, public or synthetic scenarios.

3. IPR Verified security boundary

IPR Verified is the private-verification profile. It may use tax-code and valid identity-document evidence only under a private verification boundary.

Accepted document categories for the target model are:

  • identity card / CIE;
  • passport;
  • driving license.

These materials are security-sensitive. They must not be stored in GitHub Pages, public registry files, public issues, public commits, public demo surfaces or browser-only public tools unless a dedicated private, secure and legally reviewed environment exists.

4. System security hierarchy

IPR
IPR is the base operational product. Its security role is to connect an operational identity reference to event context, proof material, responsibility and verification. It is not a legal identity system, public identity-custody database or regulated KYC / AML service.
IPR Verified
IPR Verified is the private-verification profile. It improves operational seriousness through controlled identity verification, but it does not create cybersecurity certification, legal identity certification, eIDAS qualification or regulated KYC / AML provider status by itself.
IPR AI Audit Trail
IPR AI Audit Trail is the first MVP use case. Its security boundary requires authorized documents, document hashing, human validation, EVT continuity, OPC proof and audit-ready reporting.
JOKER-C2
JOKER-C2 is a runtime demonstrator for governed AI-assisted workflows. It is not a production security platform, SOC replacement, incident-response system, command system or autonomous compliance authority.

6. Public data minimization

The public layer should expose only minimized proof data. Public records should use fields such as:

  • entity_type
  • subject_label
  • operator_label, where applicable
  • record_scope
  • verification_level, where applicable
  • payload_sha256
  • evt_id, where applicable
  • opc_id, where applicable
  • timestamp
  • status

A public label is not a full identity record and does not replace private identity verification, contractual qualification, institutional validation, cybersecurity assurance or legal authorization.

8. Demo and pilot security boundary

Public demos and R&D tests must use only synthetic, public, owned or expressly authorized materials. Users must not upload or paste secrets, private keys, credentials, tax codes, identity documents, customer personal data, confidential third-party data, production logs, private prompts, private outputs or regulated evidence requiring protected handling.

Any external pilot involving real or sensitive data, including real identity verification for IPR Verified, requires a separate environment with legal basis, responsibility allocation, security controls, privacy controls, retention rules, access controls and contractual scope defined before use.

9. Fail-closed interpretation

The fail-closed model avoids uncertain success states. When a required condition is not satisfied, the workflow must block, deny, escalate or require manual review.

  • missing input → INVALID;
  • malformed hash → INVALID;
  • registry unavailable → NON_OPERATIONAL;
  • registry schema mismatch → NON_OPERATIONAL;
  • missing public record → NO_PUBLIC_RECORD;
  • hash mismatch → HASH_MISMATCH or INVALID;
  • tax code or identity document in the public layer → block, removal or review;
  • forbidden public field detected → block, removal or review.

10. Defensive security scope

Authorized security review is limited to defensive analysis of repository-owned code, documentation, public pages, registry records, schemas, tools and explicitly authorized systems.

The project does not authorize unauthorized access, exploitation of third-party systems, malware development, credential theft, evasion, data exfiltration, destructive testing, offensive cybersecurity operations, persistence, covert access, privilege escalation, command-and-control activity or harmful automation.

12. Incident reconstruction

When a technical or governance incident requires reconstruction, the minimum review path is:

  1. identify the relevant IPR, public registry entry, EVT reference, OPC proof or audit trace;
  2. retrieve private evidence only through authorized private channels;
  3. compute SHA-256 over the controlled artifact;
  4. compare the result against the public payload_sha256 commitment or expected proof reference;
  5. review append-only history, audit findings, commits and issue traces;
  6. fail closed if required evidence is missing, inconsistent or unverifiable.

13. Security reports

Security reports should follow the repository security policy. Reports must remain defensive and should not include secrets, private keys, credentials, tax codes, identity documents, private communications, customer data, private prompts, private outputs or sensitive payloads in public issues.

If sensitive material is discovered, do not copy, redistribute, exploit, index or amplify it. Report the issue according to SECURITY.md.
