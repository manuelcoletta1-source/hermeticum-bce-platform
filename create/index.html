Create or prepare an IPR record.

This page is the operational gateway for creating or preparing an Identity Primary Record. IPR is the base product of the HBCE ecosystem: it connects an operational identity reference, an event context, proof material, responsibility and later verification.

In the target verified model, a human IPR is created through a private identity-verification workflow based on tax-code and valid identity-document evidence. Accepted document categories are identity card / CIE, passport or driving license. The public registry does not store identity documents, tax codes, document numbers or personal payloads. It stores only minimized proof references.

1. What “Create IPR” means

Creating an IPR means preparing an operational identity record that can later be connected to private verification evidence, hash-oriented proof, event records, proof receipts and verification outputs. The purpose is not to replace legal identity systems, digital signatures or public registries. The purpose is to give HBCE a stable operational reference for traceable digital execution.

In practical terms, an IPR creation flow should produce or prepare a private operational record, compute proof material, connect it to evidence references and make it possible to verify whether the record still matches the available evidence.

2. Private verification model

IPR separates private identity verification from public proof. This is the core privacy and compliance posture. Identity evidence may be used privately to create or verify the IPR, while the public layer remains minimized. 

PRIVATE VERIFICATION
→ tax code
→ valid identity document
  - identity card / CIE
  - passport
  - driving license
→ private evidence package
→ IPR verified record
→ hash-oriented public proof reference
→ verification / audit / EVT / OPC

Tax code, document number, document scan, portrait image, address, date of birth and personal payload must remain outside the public registry and outside public proof records.

4. Operational flow

The creation process should remain simple and reconstructable. Private verification prepares the identity boundary, IPR creation generates the operational record, proof material is generated next, evidence is registered or referenced, and the record is verified before it is presented as operationally valid. 

Private verification
→ create IPR record
→ generate hash-oriented proof material
→ register or reference minimized evidence
→ verify record and proof
→ use IPR in HBCE workflows

If the proof is missing, inconsistent or unverifiable, the system should not present the record as valid.

7. What this page does not claim

This creation gateway must be read within the current R&D/MVP boundary. It supports technical creation, private verification preparation, proof generation and verification workflows, but it does not claim to issue official legal identity, replace legal identity systems or operate as a regulated certification authority.

  • It does not create a public legal identity.
  • It does not replace SPID, CIE, EUDI Wallet, eIDAS schemes, digital signatures or public registries.
  • It does not provide legal certification or regulated trust-service status by itself.
  • It does not make a record legally binding without external legal, contractual or institutional validation.
  • It does not authorize production use with secrets, private keys, credentials or sensitive third-party data.
  • It does not allow identity documents, tax codes or document numbers to be stored in the public registry.

Use only synthetic, public or authorized materials in demo and pilot contexts. Identity evidence belongs only in the private verification layer under an appropriate legal, privacy and security boundary.
