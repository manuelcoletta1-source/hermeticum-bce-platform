2. Why the old approval console is removed

The previous version implemented a browser-side workflow that suggested root-gated approval, payment confirmation, final license generation, registry entry generation and network record generation.

Even if the previous implementation was local and browser-side, the wording and outputs could be misread as an active operator approval or license issuance process. To avoid overclaiming, the active console has been removed.

Any future approval workflow would require separate legal review, privacy review, security review, contractual framework, evidence retention policy, access control, human authorization, revocation policy, and clear distinction between public proof and private evidence.

3. Current public proof model

If a future operator approval or authorization process is developed, public proof should follow the current HBCE model: 

Private or controlled evidence
→ canonical hash commitment
→ payload_sha256
→ registry v3 public record
→ deterministic verify
→ PUBLIC_RECORD_PRESENT / NO_PUBLIC_RECORD / INVALID / NON_OPERATIONAL

Public proof presence does not equal operator approval. A public proof record only indicates that a minimized public proof commitment exists.
