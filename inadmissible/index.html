NON-ADMISSIBLE · EXECUTION BLOCKED

Examples of non-admissible systems

This page provides structural examples of systems that become non-admissible under the HBCE Baseline. No vendor names. Only properties. Non-admissible means: execution must be blocked.

Non-admissible patterns

1) Non-reproducible decisions

If the same input cannot reproduce the same decision outcome (or a bounded, deterministic set of outcomes), verification cannot be independent. The decision is non-admissible for execution.

2) Missing evidence references

If an action cannot be tied to a canonical manifest and deterministic hash, there is no admissible evidence chain. Missing match → non-admissible.

3) Editable logs / mutable history

Systems whose audit trail can be rewritten cannot provide definitive accountability. Corrections must be append-only. Mutable history → non-admissible.

4) Replaceable AI instances without identity continuity

If an AI model is swapped or updated without identity continuity, responsibility fragments. Without a persistent identity trajectory, execution becomes disputable → non-admissible.

5) Silent fallback behavior

If verification fails and the system “keeps going”, it is not fail-closed. Silent fallback converts verification into theater. Non-admissible.

6) Evidence depends on platform trust

If verification requires trust in the operator’s platform rather than independent reproduction, the evidence is not admissible in high-accountability environments.

Operational consequence

In a fail-closed baseline, non-admissible states are blocked. Execution is permitted only when evidence is reproducible and matched.

HBCE does not accuse vendors. It defines admissibility conditions. Systems that cannot satisfy them become structurally obsolete in high-accountability environments.
