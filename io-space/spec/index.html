IO-SPACE SPEC

Specifica operativa per certificazione eventi: manifest canonico → hash deterministico → prova minimizzata (hash-only) → registro append-only. Se una condizione fallisce → FAIL-CLOSED.

1. Scopo

IO-SPACE definisce un modello deterministico per rendere azioni, decisioni e transizioni di stato certificabili e verificabili nel tempo. Il modello è progettato per sistemi ad alta responsabilità (robotica, infrastrutture, energia, sanità, istruzione, spazio, contesti regolati).

Pubblicazione: proof-only. In pubblico: solo hash e timestamp (minimizzazione). Nessuna custodia pubblica di dati operativi o personali.

2. Definizioni

Event Manifest
Documento strutturato che descrive un evento in forma canonica (campi + ordine + normalizzazione).
event_hash
Hash deterministico derivato dal manifest canonico. Deve essere riproducibile e verificabile.
Proof (hash-only)
Rappresentazione pubblica minimizzata dell’evento: hash + timestamp (+ metadati non sensibili).
Nota
“Verificabile” significa: un terzo può calcolare lo stesso hash partendo dallo stesso manifest canonico. Se non può, non esiste opponibilità.

3. Requirements (obbligatori)

R-01 — Determinismo
Il calcolo di event_hash deve essere deterministico. Stesso input canonico → stesso output.
R-02 — Canonicalization
Il manifest deve essere normalizzato (campi richiesti, ordine stabile, encoding stabile). Nessuna ambiguità.
R-03 — Proof-only in pubblico
In pubblico si pubblica solo prova minimizzata (hash-only). Dati operativi e personali restano fuori dal registro pubblico.
R-04 — Append-only
Il registro deve essere append-only. Niente riscritture. La storia è parte della sicurezza.
R-05 — IPR link (quando applicabile)
Gli eventi ad alta responsabilità devono poter essere collegati a identità operative (IPR) e ruoli verificabili.
R-06 — Fail-closed
Se un requisito non è soddisfatto → INVALID. Non esistono “validazioni parziali”.

4. Modello di verifica (deterministico)

Pipeline
  1. Input: event manifest (canonico).
  2. Compute: calcolo deterministico di event_hash.
  3. Compare: match con proof nel registry pubblico (hash-only) o nel ledger interno (se applicabile).
  4. Output: VALID se match. Altrimenti INVALID.
IO-SPACE non chiede fiducia. Chiede match deterministico.

5. Failure modes (FAIL-CLOSED)

F-01 — Manifest non canonico
Campi mancanti, ordine instabile, encoding ambiguo → INVALID.
F-02 — Hash non matcha
event_hash calcolato ≠ proof in registry → INVALID.
F-03 — Fonte non leggibile
Registry/nodes source non leggibile o incoerente → INVALID.
F-04 — Timestamp incoerente
Timestamp mancante o non conforme al formato accettato → INVALID.
F-05 — Violazione minimizzazione
Tentativo di pubblicare dati sensibili nel registro pubblico → BLOCK.
F-06 — Identità non valida
Se richiesto link a IPR e IPR non è VALID → INVALID.

6. Modello pubblico (proof-only)

Principio

La superficie pubblica è minimizzata: in pubblico esiste solo la prova. L’operatività reale vive fuori dal registro pubblico, ma resta verificabile tramite hash.

Pubblico
hash + timestamp (+ metadati non sensibili). Niente PII. Niente payload operativi.
Privato / Operativo
manifest completo, contesto e dati operativi custoditi da chi ha titolo. La prova pubblica rimane verificabile.
