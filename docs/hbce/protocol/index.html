This specification is designed to be implementable and demonstrable. It is not a legal opinion and does not attribute responsibility. It defines technical primitives and deterministic verification logic.

1. Purpose

HBCE Protocol v1.0 defines a minimal, verifiable identity infrastructure for entities operating in digital environments: humans, AI systems, machines, organizations, and critical infrastructures. The protocol defines the structure of an Identity Primary Record (IPR), an append-only registry model, deterministic verification rules, a time-based certification mechanism, and operational state management under fail-closed constraints.

The objective is technical and demonstrative: provide a system where operational truth can be checked independently (replicable verification) while preserving EU-aligned constraints such as data minimization and no public custody of personal data.

2. Foundational Principles

  • HASH_ONLY — public layer exposes proofs (hashes) and minimal metadata, not personal data.
  • APPEND_ONLY — events are never rewritten or deleted; history is immutable.
  • FAIL_CLOSED — if verification fails, the result is INVALID.
  • GDPR_MIN — minimization by design; the protocol avoids public data custody.
  • STATE_SEPARATION — identity (who/what) is separated from authorization (what it can do).

3. Layered Architecture

Layer 0 — Identity Primary Record (IPR)

Persistent identity object: identifier, root hash, timestamps, status, optional public key.

Layer 1 — Append-Only Registry

Immutable records/events referencing hashed payloads; no retroactive modification.

Layer 2 — Deterministic Verification

Replicable checks: hash matching + state rules + optional signature validation.

Layer 3 — Time Certification (Renewal)

Cyclic certification; overdue identities freeze by rule; renew emits append-only events.

Layer 4 — Operational Authorization

Licenses/capabilities derived from but distinct from the base identity.

Layer 5 — Governance & Versioning

Protocol evolution is versioned; changes are append-only (no rewriting history).

4. Data Objects (v1.0)

4.1 IPR Minimal Fields

  • ipr_id (string)
  • root_hash (SHA-256 hex)
  • creation_timestamp (ISO 8601)
  • public_key (optional in v1.0; recommended)
  • status = ACTIVE | INACTIVE | FROZEN | REVOKED | ARCHIVED

4.2 Registry Record (base)

  • record_type (e.g., STATUS_UPDATE)
  • ref_payload_hash (SHA-256 hex)
  • timestamp (ISO 8601)
  • event_hash (SHA-256 hex)
  • signature (optional in v1.0)

4.3 Event Example

{
  "record_type": "STATUS_UPDATE",
  "ref_payload_hash": "<sha256>",
  "status": "ACTIVE",
  "timestamp": "2026-02-19T00:00:00Z",
  "event_hash": "<sha256>"
}

v1.0 is intentionally minimal: signatures are optional but recommended; consensus is not included in the demonstrator layer.

5. Deterministic Verification Rules

Deterministic verification must be replicable by an independent verifier given the same input payload and public registry records. If any required check fails, the result is INVALID (fail-closed).

  1. Hash: compute H = SHA-256(payload).
  2. Match: verify H matches ref_payload_hash in the registry record.
  3. State: verify the referenced IPR is not REVOKED.
  4. Certification (if enabled): if now > next_due treat as FROZEN by rule.
  5. Signature (optional v1.0): if present, verify against the declared public key.

Same inputs must produce the same result: VALID / INVALID.

6. Time Certification (Renewal)

HBCE supports an optional periodic certification cycle. If a certification window expires, the system freezes the IPR by rule, and a renewal emits an append-only event.

  • last_certification (ISO 8601)
  • next_due (ISO 8601)
  • certification_level (string)
If now > next_due:
  status = FROZEN
  emit append-only event (STATUS_UPDATE)

7. Operational Authorization (State Separation)

HBCE separates identity from permission. Licenses are derived from identity but represented as distinct objects and state flows.

  • Operator
  • Node
  • Enterprise
  • Infrastructure

8. Governance & Versioning

Versions follow HBCE-PROTOCOL-vMAJOR.MINOR. Updates must not rewrite historical events. Validation must remain deterministic within a declared version.

  • No retroactive deletion/modification of historical records.
  • New rules must be explicit and versioned.
  • Determinism is mandatory.

9. EU Compliance Mapping (technical)

GDPR

  • Public layer is hash-only; no personal data required for public verification.
  • No public custody of personal data by design.

NIS2

  • Immutable event logs + measurable states support auditability and operational continuity.

eIDAS 2.0

  • Can integrate with trust services (signatures/timestamps) depending on implementation.

AI Governance

  • AI systems can be assigned IPRs; state changes become auditable events.

10. Threat Model Summary

Designed to mitigate

  • Retroactive log tampering
  • Identity impersonation via unverifiable states
  • Untracked state changes
  • Payload falsification (hash mismatch)

Not fully addressed by v1.0

  • Endpoint compromise
  • Private key theft
  • Physical attacks
  • Automated distributed consensus

11. v1.0 Limitations

  • No automated distributed consensus layer
  • Digital signatures optional (recommended)
  • No built-in advanced encryption layers
  • No automatic cross-border interoperability workflows

v1.0 is a demonstrator: minimal, functional, auditable. Later versions can harden issuance rules, signatures, and inter-operator governance under append-only constraints.
